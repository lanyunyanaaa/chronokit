# ChronoKit 开发方案 · 使用优先版

> 2026-09-29 · PM 视角 · 约束条件：**只考虑使用**（不优化发布、传播、获客）
> 本版（v2）取代同日早间的"发布优先版"路线图：旧版以 GitHub 下载量为北极星，M0 的一半内容（CI、Release 渠道、README 转化文案、渠道提交）属于传播工作，与本约束冲突，全部移出。状态：待确认，确认后从 U0 开始。

---

## 0. 一句话判断

以"使用"为唯一标尺，ChronoKit 的问题不再是"产品不存在"，而是**每次真实使用都会在五个断点上卡住**：不知道文件有没有问题（无发现入口）、修起来只能逐个文件（无批量工作台）、修完文件名还是 mmexport（无重命名）、第二天打开从头再来（无会话记忆）、库里一半是照片但工具看不见（无 EXIF）。方向 = **U0 能用 → U1 好用（日常闭环）→ U2 用得上全部文件（照片）→ U3 用得长久**。

---

## 1. 评判标准（与上一版的唯一差异）

优先级公式：**使用价值 = 使用频率 × 覆盖文件比例 × 解决深度**。

由此产生三个与旧版不同的结论：

1. **包装工作压缩到"能用"的最小集**（U0 只留 1-2 天）：安装包、内置 ffmpeg、图标是使用前提，保留；CI、Release 运营、README 转化优化、渠道提交是传播手段，剔除。
2. **"每天用"的小功能优先级上升**：会话保存、记住媒体库路径这类旧版排在 M1 末尾的便利项，在使用标尺下是动线起点，提前。
3. **度量方式改变**：产品明确不做遥测，所以不设下载量类北极星。验收全部改为**本地可执行的 dogfood 场景标准**（每个里程碑给出具体场景与耗时上限）。

## 2. 用户使用动线：现状 vs 目标

**现状动线**（只对"知道问题在哪"的专家可用）：
带着明确问题来 → 手动挑工具 → 逐个/小批修 → 依赖历史页撤销。

**目标动线**（对最大用户群可用）：
打开应用 → 自动恢复上次会话 / 点"我的媒体库" → 体检报告（哪里有问题、多严重）→ 表格里看+改，或一键生成修复计划 → dry-run 确认 → 执行 → 备份中心兜底、随时撤销。

五个断点与对应解法：

| # | 断点 | 用户表现 | 解法 | 阶段 |
|---|---|---|---|---|
| 1 | 无发现入口 | "相册好乱但不知道哪乱" | 体检中心（扫描→报告→修复计划） | U1 |
| 2 | 无批量工作台 | 逐个文件改，500 个文件改到放弃 | 批量编辑表格 | U1 |
| 3 | 文件名无意义 | 修完时间，资源管理器还是 mmexport 一片 | 智能重命名（时间→文件名） | U1 |
| 4 | 无会话记忆 | 第二天打开，重新选文件夹重新等 | 会话保存 + 媒体库路径记忆 | U1 |
| 5 | 照片不可见 | 库里照片+视频混着，工具只认视频 | EXIF 读写（拆成读/写两步） | U2 |

## 3. 功能优先级矩阵（打分依据）

评分 1-5。频率=多久用一次；覆盖=能处理用户库中多少文件；深度=解决的痛有多根。

| 候选 | 频率 | 覆盖 | 深度 | 综合 | 结论 |
|---|---|---|---|---|---|
| 体检中心 | 5（每次使用的入口） | 4 | 5 | **14** | U1 核心 |
| 批量编辑表格 | 5（每次使用的工作台） | 4 | 4 | **13** | U1 核心 |
| 会话/路径记忆 | 5（每次打开） | 5 | 3 | **13** | U1 先做（成本 1 天） |
| 智能重命名 | 4 | 5 | 4 | **13** | U1 |
| 备份中心 UI | 3（出问题时） | 5 | 4 | **12** | U1 |
| EXIF 只读 | 5（接入后每次） | 照片≈库的一半 | 4 | **13** | U2a（读的成本仅约写的 1/3） |
| EXIF 写入 | 3 | 照片 | 5 | **11** | U2b |
| 安装包+内置 ffmpeg | 1（一次） | 5 | 5 | 前提 | U0 |
| 应用图标 | 1 | 5 | 2 | 前提 | U0 |
| 自动更新 | 1（偶尔） | 5 | 2 | 8 | U3 |
| CLI | 2（技术用户） | 5 | 3 | 9 | U3 |
| mac/linux 适配 | 2 | — | 3 | 8 | U3 |
| ~~CI / Release / 渠道 / README 转化~~ | 0（非使用） | — | — | 剔除 | 未来要发布时另立方案 |

关键取舍：**EXIF 拆成读和写两步**。"读"接入 TimeSource 后，体检/检查器/表格/重命名/同步/时间工具六个功能立即对照片生效（重命名和同步根本不需要写 EXIF）；"写"只影响"把时间写回照片"一个动作。先读后写，用 1/3 的成本拿到 5/6 的使用收益。

## 4. 里程碑详情

### U0 · 可用基线 v0.1.1（1-2 天）

现状核实（比旧方案估计的好）：`electron-builder.yml` 已存在（NSIS 可选目录 + 便携版、extraResources 打包 ffmpeg），`ffmpeg.ts` 三级回退链已就绪。真正缺的只有三件事：图标、ffmpeg 二进制、以及从未真正跑通过打包。

1. **应用图标**：SVG 设计（时钟 + 播放三角，#1677ff 主蓝），脚本生成 ico/png（含 256px 及安装器系列尺寸）到 `build/`。
2. **ffmpeg 落地脚本**：从系统 PATH（本机 6.1.3）或 LGPL essentials 构建复制 ffmpeg/ffprobe 到 `resources/ffmpeg/`；electron-builder `beforePack` 钩子校验存在，缺则报错拒绝打包；目录不进 git（.gitignore 补 `resources/ffmpeg/`、`release/`）。选 LGPL 构建规避 GPL 传染。
3. **跑通并验证打包**：`dist` 产出安装版 + 便携版；在无开发环境的目录做冒烟——安装、启动、扫描一个文件夹、执行一次批量偏移、撤销。
4. **README 压缩为使用文档**：安装 → 三步上手（选文件夹/加文件 → 选工具 → 执行并撤销）→ 常见问题（SmartScreen 未签名说明）。不做英文双语文案、不加截图营销位，能用即可。

**验收（dogfood 场景）**：找一台只装了 Windows 的机器（或干净沙盒），双击安装版完成一次完整修复；便携版解压双击同样可用。

**明确剔除**：GitHub Actions CI、Release 发布运营、双语 README、推广渠道提交。这些是传播工作，若未来决定公开发布，另立方案补齐。

### U1 · 日常使用闭环 v0.2.0（约 2 周）

> 前置：U0 之后建议插入"重构前置周"（约 4.5 天）——性能四连修（probe 并发+缓存、缩略图协议、硬链接备份、虚拟化）与 UI 架构重排（归一化 store、共享组件原语），详见 [PERF-AND-UI-REFACTOR.md](PERF-AND-UI-REFACTOR.md)。体检/表格两个重页面直接建在这些地基上，避免二次返工。
>
> **进展 2026-09-29**：以下能力已提前落地——probe 6 路并发 + 渲染层分块渐进回填；`ck-thumb://` 协议 + 缩略图改为**读取 Windows Shell 缓存**（`IShellItemImageFactory`/持久 PowerShell worker，不再 ffmpeg 提取，视口内懒加载）；最近导入文件夹记忆（`.data/recents.json` + 各面板下拉）；**智能导入**（根文件夹递归扫描 → 归一化同名分组 → 双文件组"大者为源"自动配对 → 3+ 同名弹窗确认 → 未配对进目标列表），核心逻辑在 `src/core/smart-import.ts` 含单测。U1 剩余：probe 磁盘缓存、虚拟化、体检中心、批量表格、智能重命名、备份中心 UI、会话完整保存。
>
> **进展 2026-10-02（U1 全部落地）**：U0 打包基线同日完成（图标、ffmpeg 落地脚本、安装版+便携版冒烟、使用文档 README）。U1 四件套全部实现——**会话记忆**（`session.json` 快照：五个列表+页签+阈值+表格编辑态，启动自动恢复并提示；`window.json` 恢复窗口位置/大小/最大化；`SessionBridge` 防抖持久化）；**体检中心**（`src/core/checkup.ts` R1-R7 规则引擎，17 单测；报告页统计卡+按规则清单+展开文件明细+单条/全部"预览修复"，修复完全复用 plan→dry-run→exec→undo）；**批量表格**（antd Table 虚拟滚动，时间单元格点击编辑、三列排序、目标列+设值/偏移/列间复制批量操作、脏标记、`buildEditsPlan` 出计划）；**智能重命名**（`src/core/rename.ts` 三模板+前后缀+冲突跳过/编号，10 单测；journal 新增 rename 操作类型，撤销=改名回去；`buildRenamePlan` 纯函数、执行时主进程二次查重）；**备份中心**（按批次分组展示 journal 备份、空间统计、单文件还原、批次/单文件删除与 30 天清理，路径校验只允许删 backupDir 内文件）。CK_SHOT 扩至 17 张截图（8 空态+9 载入/弹窗）。

顺序即动线顺序。信息架构微调：侧边栏分三组——发现（体检、检查器）/ 修复（同步、时间工具、重命名、表格）/ 安全（备份中心、历史），不做大改版。

#### 4.0 会话与路径记忆（先做，约 1 天，动线起点）

- 渲染层 store persist（文件列表、匹配结果、表格编辑态、页签）+ 主进程 `.data/session.json`。
- "我的媒体库"：记住上次扫描的文件夹，各页顶部一键载入；窗口位置大小恢复；启动提示"恢复上次会话（N 个文件）"。

#### 4.1 体检中心（本里程碑核心）

- 输入：拖拽/选择文件夹，递归扫描 + ffprobe 缓存（`.cache`），万级文件分批并发、可取消、不卡 UI（沿批量任务既有模式）。
- 规则引擎（纯 TS 于 `src/core`，全部可单测）：

| # | 规则 | 级别 | 一键修复动作 |
|---|---|---|---|
| R1 | 元数据 creation_time 缺失/占位（1900/1970 附近） | error | 时间工具·从文件名解析（预填） |
| R2 | 文件名时间与元数据时间冲突（默认容差 60min） | warn | "以文件名为准"批量计划 |
| R3 | NTFS 创建时间晚于修改时间（转存特征） | info | 创建时间同步到文件名/元数据时间 |
| R4 | 同批文件时间全部相同（方差 0，≥3 个） | error | 以文件名时间重排全部 |
| R5 | 文件名时间单调但元数据乱序（相册乱序实证） | warn | "以文件名为准"批量计划 |
| R6 | 批次内一致的小时级偏移（疑似时区） | warn | 批量偏移 ±Xh（预填） |
| R7 | ffprobe 无法解析 / 0 字节 / 异常时长 | error | 仅标记 |

- 报告 UI：统计卡（健康/提示/警告/异常三色）+ 问题清单（按规则过滤），每条跳转对应工具或展开一键修复。
- **架构原则：体检不新建写操作管道，只生成"修复计划"，完全复用 plan → dry-run → executor → journal → undo。** 这是 U1 成本可控的原因。

#### 4.2 批量元数据编辑表格

- 行=文件，列=缩略图（`thumbs.ts` 已有）| 文件名 | 元数据时间 | 修改时间 | 创建时间 | 时长 | 状态；虚拟滚动保证数百行流畅。
- 表头按任一时间列排序——让用户"看见"乱序；单元格可编辑；多选批量：设固定值 / 偏移 / 列间复制。
- 脏标记 → 底部"应用 N 项变更" → 复用 dry-run → 执行 → 可撤销。

#### 4.3 智能重命名

- 方向：时间 → 文件名（反向的"文件名 → 时间"已在时间工具）。
- 模板预设（`YYYYMMDD_HHMMSS` / `YYYY-MM-DD HHMMSS` / 原名加日期前缀）+ 前缀/后缀 + 冲突策略（跳过/追加序号）；时间来源复用 time-engine 优先级链；dry-run 对照表。
- **journal/executor 扩展 rename 操作类型**——U1 唯一动核心管道的点，保证重命名可完整撤销。

#### 4.4 备份中心 UI

- journal 已有数据，只缺界面：按会话分组（时间/文件/操作/大小/状态）；单个/批量还原；空间占用统计；超阈值（默认 5GB，可配）提示按年龄清理（二次确认）。

**验收（dogfood 场景）**：准备 500+ 文件的混合库（微信转存 + 相机 + 录屏），从打开应用到"体检 → 表格修 → 一键修复 → 抽查撤销"全流程 ≤ 10 分钟；重命名后撤销能完整还原原名；中途关掉应用，重开后会话完整恢复。

### U2 · 使用覆盖面：照片 v0.3.0（约 2 周，拆两步）

#### U2a · EXIF/XMP 只读（3-4 天，先做）

- TimeSource 抽象落地：视频容器 / EXIF DateTimeOriginal+OffsetTime / 文件名 / 文件系统四源统一优先级链，`time-engine` 扩展。
- 格式：JPEG、PNG（eXIf chunk）、HEIC 读取先行；RAW 不承诺。
- 生效范围即刻扩大：体检规则、检查器、表格、智能重命名、时间工具全部对照片可用；同步配对在照片上退化为尺寸 + 内容 hash（时长匹配失效）。
- 这一步做完，"照片+视频混合库"的用户立即从"半库不可用"变为"全库可管理"。

#### U2b · EXIF 写入（7-10 天，后做）

- JPEG 先行：写入 DateTimeOriginal、CreateDate、OffsetTimeOriginal + 文件系统三时间；写入前照旧备份进 journal、可撤销。
- PNG/HEIC 写入分级承诺（HEIC 二期），UI 上未支持格式置灰 + tooltip 说明。
- 产品文案升级：video timestamps toolbox → **media timestamps toolbox**。

**验收（dogfood 场景）**：把一卷"手机导出的照片+视频"（创建时间全是拷贝日）导入，全部修正为拍摄时间并在资源管理器按时间正确排序；照片修正可撤销且撤销后 EXIF 与文件时间均还原。

### U3 · 用得长久 v0.4 → v1.0（约 1 周）

- **自动更新**：electron-updater（GitHub Releases provider）——用户无感拿到修复，使用连续性。
- **跨平台**：mac dmg（用 birthtime）、linux AppImage/deb（仅 mtime+元数据）；平台不支持的能力 UI 置灰 + tooltip；README 功能矩阵表。
- **CLI**：复用 `src/core` 发 npm 包，`npx chronokit fix ./folder --from filename`——服务脚本化使用这一合法使用方式。
- 打 v1.0.0：承诺计划/文件格式稳定性。

## 5. 明确不做（本约束下更新）

播放器、剪辑、转码、水印、云同步、账号体系、任何遥测（"100% local" 写进使用文档首屏）；
**以及一切发布运营工作**：CI、Release 运营、渠道投放、下载量指标、双语转化文案。

## 6. 风险（只保留影响使用的）

| 风险 | 对策 |
|---|---|
| ffmpeg 分发许可 | 用 LGPL essentials 构建，使用文档声明来源与许可 |
| 无签名 → SmartScreen 拦截 | 使用文档一句话说明"更多信息→仍要运行"；不投入签名预算 |
| 万级文件体检卡顿 | 分批并发 + probe 缓存 + 可取消 |
| HEIC/RAW 范围失控 | 分级承诺：JPEG/PNG 先行，未支持格式 UI 明示置灰 |
| 平台时间语义差异 | 功能矩阵表 + 不支持项置灰，绝不静默降级 |
